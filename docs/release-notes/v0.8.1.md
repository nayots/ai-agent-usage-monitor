## Highlights

**The Codex card works again on codex-cli 0.154.0.** If you updated Codex recently, the card stopped
reporting and showed `The last read failed - codex app-server closed stdout before an id:2 response
was observed`. Nothing was wrong with your account, your quota or your sign-in. The widget was
launching Codex with a command-line flag value that 0.154.0 had removed, and Codex was refusing to
start at all.

**When a provider's CLI refuses to start, the card now says why.** That failure was invisible for
the worst possible reason: the widget read only what Codex printed on its output stream, and Codex
had written its complaint to the error stream instead. The error the card showed was accurate and
told you nothing. It now carries the CLI's own sentence.

---

## What broke

Codex takes an `--ask-for-approval` flag. Through 0.144.6 it accepted a value called `untrusted`,
and that is what this application had passed since v0.3.0 — deliberately, as one of two flags that
cap the process it spawns.

codex-cli 0.154.0 narrowed that flag to two values, `on-request` and `never`. An unrecognised value
is rejected by Codex's argument parser *before* the server it would have started ever runs, so the
process exited immediately having printed nothing at all where the widget was listening:

```
error: invalid value 'untrusted' for '--ask-for-approval <APPROVAL_POLICY>'
  [possible values: on-request, never]
```

The widget saw a stream that closed without an answer and reported exactly that. Every Codex reading
failed, every two minutes, for as long as the updated CLI was installed.

## What changed

The flag now passes `never`, which is both valid and the closer match to why the flag was there.
`never` means the model is never asked for approval and so can never be granted any, leaving the
spawned process unable to escalate beyond the read-only sandbox it is already confined to.
`on-request` would have left it able to ask.

Verified live against codex-cli 0.154.0: the rate-limit response comes back with an identical set of
fields and identical values to an unflagged call, so nothing about what the card displays has
changed — only whether it displays.

## The part that will matter next time

The reason a one-word flag change took a manual investigation is that the widget threw away the only
account of the failure that existed. A provider's CLI writes its complaints to a separate stream,
and that stream was being redirected and then never read.

It is now drained from the moment the process starts, and when a launch fails the card shows what
the CLI said:

> codex app-server closed stdout before an id:2 response was observed. It reported: error: invalid
> value 'untrusted' for '--ask-for-approval &lt;APPROVAL_POLICY&gt;' [possible values: on-request, never]

The text is flattened to one line and capped in length so a chatty CLI cannot crowd out the rest of
the card. Reading that stream also removes a latent hazard: a redirected pipe that nobody empties
can fill up and stall the process writing to it.

## Notes

- This affects **Codex only**. Claude Code and Cursor were never involved.
- If you are still on an older codex-cli, this release works there too — `never` has been a valid
  value for far longer than `untrusted` was.
- Codex remains an **official** mechanism, and the flags remain defence-in-depth: this application
  never opens a Codex session, so nothing it does today depends on them.
